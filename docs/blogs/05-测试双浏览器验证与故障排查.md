# 第五篇：测试、双浏览器验证与故障排查

> 本篇目标：知道每类测试能证明什么，并能从浏览器现象沿着连接、事件、数据库和 React 状态逐层定位问题。

[上一篇](./04-React实时通知与异步竞态处理.md) · [返回系列目录](./realtime-team-invitation-with-socketio.md)

## 1. 为什么“我看到一次成功”远远不够

实时功能同时跨越数据库、HTTP、WebSocket 握手、房间路由、浏览器连接和 React 异步状态。一次手工成功只证明那次环境下主路径可用，不能证明未授权连接、重复邀请、断线或路由切换是正确的。

测试应分层，每层回答一个明确问题。

## 2. 后端测试矩阵

### 2.1 鉴权服务

验证 Cookie 能正确提取 access_token、有效 JWT 返回用户、缺少或无效 Token 拒绝。这里不需要真的启动 Socket.IO，目标只是身份解析。

### 2.2 Gateway 单元测试

验证认证成功后只加入 user:{id}、认证失败不加入房间、emitToUser 只选择目标房间。它证明路由逻辑，不证明真实握手协议。

### 2.3 真实 Socket.IO 握手测试

启动 Nest 应用和 socket.io-client，携带登录 Cookie 连接，检查合法 Origin 成功、错误 Origin 和无效 Cookie 失败。这一层能发现仅靠 mock 看不到的 CORS、Cookie 与中间件装配问题。

### 2.4 Notifier 与 TeamsService

至少覆盖：新成员保存后发布一次；已有成员不保存也不通知；mock 触发 23505 时走冲突恢复分支且不再次通知；普通数据库错误原样抛出；emit 同步失败不回滚成员摘要。当前用例没有同时启动两个真实请求，因此它证明的是冲突恢复语义，不是数据库层的真实并发执行。

这些测试不应声称“客户端必达”，因为当前没有 ACK。

## 3. 前端测试矩阵

RealtimeProvider 应验证连接参数、事件进入通知队列、相同 eventId 去重、teamRefreshVersion 增长、disconnect 后 reconnect 补同步、首次失败后恢复补同步、用户切换销毁旧 session，以及旧 socket handler 无法污染新用户。

页面测试应使用可控 Promise 制造真实竞态：

~~~text
发出 team A 邀请但不 resolve
切换 team B
再切回 team A
发出新的 A 邀请
按不同顺序 resolve 两个请求
验证旧请求不能清空新输入或解除新 pending
~~~

只使用立即 resolved Promise，很多竞态永远不会被测试触发。

## 4. 双浏览器验证准备

使用两个独立浏览器配置文件或普通窗口 + 无痕窗口，避免两个标签共享同一登录 Cookie。

准备：

1. API、Web、PostgreSQL 均已启动；
2. CORS_ORIGIN 与 Web 实际地址一致；
3. Alice 是团队负责人；
4. Bob 是已注册用户但还不是成员；
5. 两边都打开 DevTools Network。

## 5. 主路径验证步骤

1. 浏览器 A 登录 Alice，进入团队管理页面；
2. 浏览器 B 登录 Bob，确认 Network 中存在 Socket.IO WebSocket 连接；
3. Alice 输入 Bob 邮箱并邀请；
4. Alice 侧 POST /api/teams/:teamId/members 返回成功；
5. Bob 的 WebSocket Frames 出现 team.membership.created；
6. Bob 立即看到邀请通知；
7. Bob 页面随后发出 GET /api/teams；
8. GET 返回后，新团队卡片出现；
9. Alice 再次邀请 Bob，应返回已有成员语义，Bob 不应出现第二条 created 通知。

注意：toast 先出现、团队卡片稍后出现是正常设计，因为卡片等待 REST 权威快照。

## 6. 断线与会话隔离验证

### 6.1 Bob 离线

关闭 Bob 浏览器后邀请。重新登录时可能没有历史 toast，但团队列表必须包含该团队。若列表也没有，问题在数据库或 REST，不是“离线消息没做”这么简单。

### 6.2 断线重连

在 DevTools 临时切 Offline，再恢复。连接重建后应触发一次团队快照同步。不要只看 Socket 状态变绿，还要看 GET /api/teams。

### 6.3 切换账号

Bob 登出并登录 Carol。旧 Bob 事件不得进入 Carol 通知队列，旧团队也不得因晚到请求出现在 Carol 页面。

## 7. 按证据排查，而不是先猜

~~~text
邀请 POST 成功吗
  -> 数据库成员关系存在吗
  -> TeamsService 是否走到 notify
  -> 服务端目标 room 正确吗
  -> Bob WebSocket 是否已连接且鉴权成功
  -> Frames 是否收到 team.membership.created
  -> Provider 是否增加通知与 refresh version
  -> GET /api/teams 是否发出并成功
  -> React 是否因上下文或竞态丢弃结果
~~~

每一步都有可观察证据。不要一看到“没有 toast”就改 React，也不要一看到连接存在就断言后端发送成功。

## 8. 常见故障表

| 现象 | 首先检查 | 常见原因 |
| --- | --- | --- |
| 登录或 API 显示获取失败 | Network 的 URL、状态、Response | 前后端端口错、旧服务进程、CORS_ORIGIN 不匹配 |
| REST 正常但 Socket connect_error | 握手请求 Origin 和 Cookie | Cookie SameSite/Secure/Domain、错误 Origin、JWT 过期 |
| Alice 成功，Bob 没事件 | API notify 日志、目标 user room、Bob Frames | Bob 邀请时离线、房间 ID 错、连接在另一 API 实例 |
| Bob 有事件但没 toast | Provider handler、eventId、当前用户 session | 重复 eventId 被去重、旧 generation 被正确丢弃、Provider 未挂载 |
| 有 toast 但没团队卡片 | GET /api/teams 的状态与响应 | REST 失败、刷新被合并后未追赶、旧请求覆盖 |
| 邀请按钮一直“邀请中” | POST Timing、路由切换、finally | 请求未结束、旧/新请求状态所有权混乱 |
| 刷新后功能正常 | WebSocket Frames 与 refresh GET | 实时通道或失效刷新有问题，数据库通常已成功 |

## 9. 浏览器 Network 应怎样看

在 Chrome/Edge DevTools 中筛选 WS，选择 Socket.IO 连接并打开 Messages/Frames。Socket.IO 帧可能带协议数字前缀，不必只用肉眼猜含义；重点确认事件名、payload 的 eventId/teamId，以及到达时间。

同时保留 Fetch/XHR 记录，核对邀请 POST 和 Bob 的 GET。一个完整成功链路应该能在时间线上看到 POST 成功、事件抵达、GET 回源三个阶段。

## 10. 自动化测试通过不等于浏览器验证完成

单元测试和构建能证明代码契约与类型成立，却不能证明本机正在运行的进程来自当前目录，也不能证明浏览器 Cookie、端口和代理配置正确。交付时应分别陈述“自动化已通过”和“双浏览器已手工验证”；没做后者就不要假装做过。

## 11. 面试一分钟版

> 我在 React + NestJS 协作工作区实现了实时团队邀请。成员关系仍通过 REST 写入 PostgreSQL，保存成功后服务端才向 user:{userId} 私有房间发布 team.membership.created。前端收到事件后先显示通知，再重新请求团队列表，所以 Socket.IO 只是低延迟提醒，REST 仍是权威数据。实现还覆盖了 Cookie/JWT 握手鉴权、Origin 限制、数据库唯一约束与 23505 幂等恢复、断线重连补偿，以及用户和路由切换时的异步竞态。

## 12. 面试三分钟展开顺序

1. 先讲痛点：邀请者成功，但被邀请者必须刷新；
2. 再讲架构：数据库事实、Socket 提醒、REST 回源；
3. 讲后端：JWT 握手、用户 room、保存后 emit、23505；
4. 讲前端：Provider、eventId、refresh version、generation；
5. 讲边界：无 ACK、离线 toast 不持久化、多实例需 Adapter/Outbox；
6. 讲验证：真实握手、23505 冲突恢复和前端竞态测试；若已经完成手工验证，再展示双浏览器 Network 证据。

这种表达比“我用了 Socket.IO 实现实时通信”更能体现完整工程思路。

## 13. 系列总结

完整闭环可以压缩为一句话：鉴权后的用户连接进入私有房间，成员关系在数据库成功提交后发布变化事件，React 收到事件立即提醒并通过 REST 获取最终快照，所有旧异步操作都必须服从当前用户与路由上下文。
