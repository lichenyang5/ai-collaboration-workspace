# 实时团队邀请通知设计

## 背景与目标

当前系统通过 `POST /api/teams/:teamId/members` 将已注册用户加入团队。邀请成功后，邀请发起者能立即看到成员列表变化，但被邀请者必须刷新工作区才能看到新团队。

本次增加一个小型实时闭环：被邀请用户在线时立即收到团队邀请通知，工作区随后通过现有 REST 接口同步团队列表。用户加入团队后可访问该团队下全部项目；本次不增加项目级成员关系，也不扩展任务实时同步。

## 范围

### 包含

- 使用 Socket.IO 建立登录用户的全局实时连接。
- 使用现有 `access_token` HttpOnly Cookie 完成 WebSocket 握手鉴权。
- 新成员关系持久化成功后，向被邀请用户发送 `team.membership.created`。
- 前端展示全局通知，并通过 `GET /api/teams` 同步权威数据。
- 连接恢复后重新同步团队列表。
- 覆盖鉴权、定向发送、事件去重、刷新合并、用户切换隔离和故障降级测试。

### 不包含

- 项目级成员表或项目级邀请。
- 任务创建、编辑、移动、归档的实时同步。
- 在线状态、聊天、已读状态或持久化通知中心。
- Redis、消息队列、数据库 Outbox 或多实例 Socket.IO 适配器。

## 设计原则

1. WebSocket 只传递“数据可能变化”的通知，REST 和数据库仍是权威数据源。
2. 实时连接失败不能阻塞登录、邀请、团队读取或项目访问。
3. 事件必须按用户定向发送，客户端不能自行订阅任意用户房间。
4. 邀请接口的成功响应不依赖实时事件是否送达。
5. 重复邀请和并发唯一键恢复不得产生重复通知。

## 后端架构

新增独立 `RealtimeModule`，由以下单元组成：

- `RealtimeGateway`：建立 Socket.IO 连接、校验握手身份、加入用户私有房间并处理断开。
- `RealtimeNotifier`：向指定用户发布强类型业务事件，隔离业务服务与 Socket.IO API。
- `TeamMembershipCreatedEvent`：定义稳定的服务端和客户端事件契约。

`RealtimeModule` 导出 `RealtimeNotifier`，`TeamsModule` 注入该服务。业务服务不直接访问 Gateway 或 Socket 实例。

### WebSocket 鉴权

客户端使用 API 基础地址连接，并设置 `withCredentials: true`。Gateway 从握手请求的 `Cookie` 头读取 `access_token`，使用当前 `JwtService` 验证签名与有效期。

验证成功后，服务端从 JWT 的 `sub` 得到用户 ID，并由服务端执行：

```text
socket.join("user:" + userId)
```

客户端不能通过消息指定或切换用户房间。Cookie 缺失、令牌无效或载荷不完整时，连接以未授权错误终止。

HTTP 与 WebSocket 共享 `CORS_ORIGIN` 允许源和凭据策略。生产环境继续依赖 Secure Cookie 与 HTTPS/WSS。

### 邀请后的事件发送

`TeamsService.addTeamMember` 保留现有权限、用户查询、幂等和唯一键竞争处理。事件仅在本次调用真正创建并保存一条新 `TeamMember` 后发送：

```text
校验负责人
→ 查找被邀请用户
→ 已存在成员：直接返回，不发送事件
→ 保存新成员成功
→ 生成响应摘要
→ 请求 RealtimeNotifier 定向通知被邀请用户
→ 返回 REST 响应
```

如果保存触发 PostgreSQL `23505` 并通过读取已存在成员完成恢复，本次调用不发送事件；真正完成插入的并发请求负责发送一次。其他数据库错误原样返回，也不发送事件。

实时发送是尽力而为。通知层捕获并记录发送异常，不能把已成功的数据库写入转换成邀请失败。第一版不使用 Outbox；用户刷新、重新登录或 Socket 重连时仍可通过 REST 恢复正确状态。

## 事件契约

事件名称固定为：

```text
team.membership.created
```

载荷为：

```ts
interface TeamMembershipCreatedEvent {
  eventId: string;
  teamId: string;
  teamName: string;
  role: 'member';
  occurredAt: string;
}
```

- `eventId` 使用新建团队成员关系 ID，供当前浏览器会话去重。
- `occurredAt` 使用 ISO 8601 UTC 时间。
- 载荷只用于提示和导航，不作为授权依据，也不直接成为团队列表数据。

## 前端架构

实时连接位于登录态路由之上、`BrowserRouter` 之内。恢复出 `currentUser` 后创建唯一连接；用户变化或登出时先使旧连接及回调失效，再断开连接和清除旧通知。

建议拆分为以下单元：

- `RealtimeProvider`：负责连接生命周期、重连处理、事件订阅和用户世代隔离。
- `useRealtime`：向页面提供通知队列和团队数据刷新版本。
- `RealtimeNotificationCenter`：顺序显示通知，支持查看团队、手动关闭和自动关闭。
- `WorkspacePage`：观察团队刷新版本，并复用 `GET /api/teams` 加载函数。

### 收到邀请事件

1. 检查 `eventId` 是否已在当前会话处理过。
2. 未处理事件进入通知队列，显示“你已加入「团队名称」”。
3. 触发团队列表重新同步，而不是直接把事件载荷插入数组。
4. 点击“查看团队”进入 `/teams/:teamId/projects`。
5. 通知采用 `role="status"`，约五秒后自动关闭，也允许手动关闭。

连续事件按接收顺序展示。多个事件到达时，团队刷新采用单飞策略：同一时刻最多一个请求；请求期间若再次失效，则当前请求结束后再执行一次，避免丢失最后一次变化。

### 重连与页面切换

首次连接成功不额外请求，因为登录恢复和工作区本身已有初次 REST 加载。发生过断线后的重新连接成功时，增加团队刷新版本，以覆盖离线期间错过的邀请。

如果工作区当前未挂载，刷新版本仍保留；用户返回工作区后执行一次同步。旧用户连接、旧请求和旧自动关闭定时器不能修改新登录用户的通知或团队状态。

## 错误处理

- 初始 Socket 连接或自动重连失败：不阻塞页面，也不覆盖现有 HTTP 错误；Socket.IO 继续退避重试。
- 团队实时同步失败：保留当前团队列表，显示“实时同步失败，可刷新页面重试”，允许后续事件或重连再次触发同步。
- JWT 失效：服务端拒绝 Socket；HTTP 接口继续通过现有认证流程决定登录状态。
- 通知发送失败：记录服务端错误，邀请 REST 请求仍根据数据库结果成功返回。
- 重复事件：按 `eventId` 忽略，既不重复提示，也不重复触发刷新。

## 依赖与配置

后端增加 NestJS Socket.IO Gateway 所需依赖，并直接声明用于 Cookie 解析的依赖；前端增加 `socket.io-client`。依赖版本与仓库现有 NestJS 11、React 19 环境保持兼容。

继续复用：

- `VITE_API_BASE_URL`：HTTP API 和 Socket.IO 的服务端基础地址。
- `CORS_ORIGIN`：允许携带凭据的浏览器来源。
- `JWT_SECRET`：HTTP 与 WebSocket 共用 JWT 验证密钥。

不新增数据库环境变量和迁移。

## 自动化测试

### 后端

- 有效 Cookie 可连接并只加入对应的 `user:{id}` 房间。
- Cookie 缺失、JWT 无效或载荷缺失时拒绝连接。
- 新成员保存成功后向被邀请用户发送一次正确事件。
- 已存在成员不发送事件。
- `23505` 唯一键恢复不由恢复请求重复发送事件。
- 数据库保存失败不发送事件。
- 通知发送失败不改变已经成功的邀请响应。
- 其他用户房间不会收到该事件。

### 前端

- 登录恢复后建立一次连接，登出和用户变化时断开并清理。
- 收到事件后按顺序显示通知并触发团队 REST 同步。
- 相同 `eventId` 只处理一次。
- 点击通知进入正确团队，手动和自动关闭均可用。
- 多个连续事件合并在途刷新，并在需要时补一次最终刷新。
- 断线重连后触发同步，首次连接不重复初始加载。
- 同步失败保留旧列表并提供错误提示。
- 旧连接、旧请求和旧定时器不能污染新用户状态。
- Socket 不可用时现有登录、邀请、项目和任务流程仍可使用。

## 手工验收

1. 浏览器 A 登录团队负责人账户。
2. 浏览器 B 登录另一个已注册账户并停留在任意登录后页面。
3. A 邀请 B 加入团队。
4. A 的成员列表正常更新，按钮恢复可操作状态。
5. B 无需刷新便看到“你已加入”通知。
6. B 打开或返回工作区，团队列表自动出现新团队。
7. B 点击通知进入该团队的项目列表。
8. A 重复邀请 B，不出现第二条实时通知。
9. B 离线后加入另一个团队，稍后登录仍能通过 REST 看到该团队。
10. 暂停 WebSocket 连接后，HTTP 登录、邀请和页面刷新仍正常工作。

## 完成标准

- 自动化测试和前后端构建全部通过。
- 两个独立浏览器会话完成手工实时邀请闭环。
- WebSocket 失败时，原有 HTTP 功能无回归。
