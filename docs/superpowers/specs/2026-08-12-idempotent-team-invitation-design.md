# 团队成员邀请幂等化设计

## 目标

修复团队成员邀请长期停留在“邀请中...”以及数据库成员与页面列表无法重新对齐的问题。邀请操作改为幂等：同一团队、同一用户重复提交时，接口返回现有成员摘要；用户尚未加入时才创建成员关系。

## 范围

- 修改团队邀请服务及其单元测试。
- 修改项目列表页邀请状态及其组件测试。
- 不修改数据库表、迁移、认证、项目或任务看板逻辑。

## API 行为

`POST /api/teams/:teamId/members` 保留负责人权限校验和邮箱用户查询：

1. 请求人不是团队负责人时仍返回 403。
2. 邮箱没有对应注册用户时仍返回 404。
3. 用户已经属于团队时，不再返回 409，直接返回现有成员摘要。
4. 用户尚未加入时创建 `team_members` 记录并返回新成员摘要。
5. 数据库唯一约束仍是并发重复写入的最终防线；若并发插入发生唯一冲突，服务重新读取成员并返回同样的成员摘要，而不是把重复操作暴露为页面错误。

接口响应保持 `TeamMemberSummary` 结构，不新增前后端协议字段。

## 前端状态与数据流

邀请开始、成功和失败由项目页 reducer 原子更新：

- `inviteStarted`：设置 `isInviting=true` 并清除旧错误。
- `memberInvited`：按成员 `id` 更新或追加列表、清空邮箱、设置 `isInviting=false` 并清除错误。
- `inviteFailed`：保留邮箱输入、设置 `isInviting=false` 并显示错误。

提交入口增加同步 pending ref。它在 React 完成下一次渲染之前就阻止第二次提交，避免快速双击产生重复请求；当前请求结束后再释放。

页面不会在提交前自行判断成员是否存在，因为数据库才是权威来源。已有成员的接口返回也走同一个成功路径，因此能够补齐页面中的缺失成员，同时不会产生重复列表项。

## 错误处理

- 权限、用户不存在和网络错误仍在页面显示原始 API 错误。
- 任意失败都必须恢复“邀请成员”按钮。
- 任意成功都必须恢复按钮，并使列表与接口返回一致。
- 不增加自动重试、轮询或全量页面刷新。

## 测试

API 测试覆盖：

- 已有成员返回成员摘要且不再次保存。
- 新成员仍正常创建。
- 并发唯一冲突后重新读取并返回现有成员。

前端测试覆盖：

- 已有成员响应被 upsert，不重复展示。
- 成功和失败后按钮恢复。
- 请求 pending 时同步重复提交只发送一个 POST。
- 新请求开始时清除上一条邀请错误。
